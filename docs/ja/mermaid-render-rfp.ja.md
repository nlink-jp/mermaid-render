# RFP: mermaid-render

> Generated: 2026-09-28
> Status: 承認済み（2026-09-28）— 独立検証 2 本の指摘と運用者判断を反映した第 2 稿

## 1. Problem Statement

gem-agent の応答に mermaid の図が出ると、いまは罫線文字の図に変換して端末に表示している
（gem-agent ADR-0042 / ADR-0063）。この方式は表現できない構文が多く、日本語が混ざると崩れやすく、
描けずにソースを見せるだけになる場面が少なくない。運用者は図を使いたいが、この品質では使えない
ので、作業の指示に図を含めていない。lagent には図を描く経路そのものが無い。さらに、変換に使っている
`AlexanderGrooff/mermaid-ascii` はコミュニティ製で、組織の方針（組織の外で書かれたコードは出荷
しない）が定まる前に採用したものである。

端末に画像を出す仕組みは両ランタイムに既にある（`internal/termimg`、iTerm2 と kitty の方式、
gem-agent ADR-0089）。そこで、mermaid のソースを画像にするエンジンを、第三者のコードを使わずに
自前で持つ。ランタイムはトランスクリプトを描くときに mermaid のフェンスをその場で画像にし、
運用者は図を画像として端末で読める。図を描けるようになれば、運用者は作業の指示に図を含める。

想定利用者は gem-agent / lagent の運用者。利用者側の準備は要らない（既定のフォントは macOS に
最初から入っているヒラギノを使い、ネットワークも資格情報も使わない）。

## 2. Functional Specification

### 使われ方（ランタイムの描画機能であって、モデルのツールではない）

- ランタイムは、応答本文をトランスクリプトに描くとき、mermaid のフェンスを見つけてこのエンジンに
  渡し、返ってきた画像をその場に表示する。モデルに図を描くツールは与えない。システムプロンプトは
  図について何も言わない（gem-agent ADR-0063 の方針をそのまま引き継ぐ）。図を求めるのは運用者の
  作業の指示である。
- トランスクリプトに保存するのは原文のまま。画像は表示にだけ使う。
- エンジンに渡すのは、gem-agent の既存の変換表（罫線レンダラ向けに形を四角に揃え、ラベル内の
  `&` を全角にする）を**通す前の原文**。通した後を渡すと、形とラベルの文字が失われる。

### Commands / API Surface

Go ライブラリ。モジュールは `github.com/nlink-jp/mermaid-render`。

| API | 役割 |
|---|---|
| `Parse(src string) (Diagram, error)` | ソースを、描き方に依存しない図のデータにする。第 2 段階の罫線表示も同じデータを使う |
| `raster.Render(d Diagram, opts Options) (*image.RGBA, error)` | 図のデータを白地のカード状の画像にする |
| `raster.RenderSource(src string, opts Options) (*image.RGBA, error)` | 上の 2 つを続けて行う |
| `raster.LoadFont(spec FontSpec) (*Font, error)` | 指定したフォントを読む。読んだものは使い回せる |
| `raster.DefaultFont() (*Font, error)` | ヒラギノ角ゴシック W3（本文）と W6（太字）を読む |

`Options` に持たせるのは次の 2 つだけ。

- `Font` — 使うフォント。省略するとヒラギノ。
- `Scale` — 拡大率。既定は **2**（段 0 の実測で決定）。本文の文字は `Scale` 1 で 14px なので、既定では
  28px になる。

PNG への変換は呼び出し側が行う（`termimg.Payload` が受け取るのは符号化済みのバイト列で、
`image.Image` を PNG にする処理は termimg に無い）。

**開発用 CLI**: `tools/` に mermaid ファイルを PNG に変換する小さな CLI を置き、make ターゲットから
使う。実機での確認と E2E に使う。リリースも配布もしない。

### 表示の大きさ

既存の `termimg.BoxFor` は写真向けの方針で、画像を最大 40 桁・画面の高さの 3 分の 1 に収める。
図をこの枠に入れると、1600×1200 の図の文字は約 5.6pt まで縮み、読めない（検証パスの試算）。
そこで図には別の枠の決め方を使う。

段 0 の実測（iTerm2 と kitty、Discussion Log）で決めた枠の決め方:

- **図の文字を端末の文字と同じ大きさに見せる。** 図の文字の高さ（em）を「セルの高さ ÷ 1.2」に
  合わせる。運用者が 0.85・1.00・1.15 倍を見比べ、両端末で 1.00 倍を選んだ。
  - 高さ（行）= 画像の高さ ÷ 図の文字の大きさ(px) ÷ 1.2
  - 幅（桁）= 画像の幅 ÷ 図の文字の大きさ(px) ÷ 1.2 × セルの縦横比（高さ ÷ 幅）
- **幅の上限は端末の幅 − 1。** 超える図は縦横比を保って縮める。文字が小さくなって読みにくいのは
  見た目の問題なので、表示を拒まない（読めなければ運用者がモデルに直すよう伝える）。
- **セルの縦横比は `TIOCGWINSZ` から得る。** これは OS から読むだけで端末への問い合わせではない
  ので、BubbleTea の実行中でも応答が入力欄に漏れない。取れないときは 2.25（termimg の想定値。
  iTerm2 の実測値と一致）を使う。端末への問い合わせ（CSI 16t など）は使わない。
- **高さには見た目の上限を設けない。** 画面より高い画像が下部固定のレイアウトとどう干渉するかは、
  組み込みの ADR で確かめて扱いを決める。
- 枠を決める関数は、組み込み先（termimg の隣）に置く。エンジンは表示の大きさを知らない。

### フォントの指定

`FontSpec{Path, Name, BoldPath, BoldName}`

- `Path` — フォントファイルのパス（.ttf / .otf / .ttc）。
- `Name` — .ttc の中から使う書体を選ぶ名前。name テーブルのフル名（ID 4）と PostScript 名（ID 6）の
  **全言語の値**と、大文字小文字を区別せずに照合する。推奨する指定値は PostScript 名
  （例: `HiraginoSans-W6`）。Font Book は日本語環境では「ヒラギノ角ゴシック W6」のような日本語名を
  出すが、それでも一致する。見つからないときは、そのファイルにある書体名の一覧を付けてエラーにする。
  `sfnt.Name` は言語を選べない（最初のレコードを返す）ので、name テーブルは自前で走査する。
  省略すると先頭の書体。
- `BoldPath` / `BoldName` — 太字（ER の実体名、subgraph の見出しなどに使う）。省略すると本文と同じ書体。

振る舞い:

1. **無い文字** — 次のどちらかに当たる文字を「その書体に無い文字」とする: 字形の番号が 0
   （`GlyphIndex == 0`）、または字形の読み込みに失敗する（`LoadGlyph` のエラー）。読み込みには
   成功しても、特定の文字の描画で失敗する書体が実在する（検証パスの実測で 9 書体）。
   `font.Drawer` の `DrawString` / `MeasureString` は、無い文字を豆腐で描き、失敗を黙って捨てるので
   使わない。文字ごとに書体を選ぶループを自前で書く。
2. **ヒラギノで補う** — 指定した書体に無い文字は、1 文字ずつヒラギノで描く。
3. **それでも無ければエラー** — ラベルから文字が欠けるのは見た目の問題ではなく間違いなので、
   欠けた画像は返さない。呼び出し側はソースを表示する。絵文字（✅ など）もヒラギノに無いので
   この扱いになる。
4. **字形を持たない文字は読み飛ばす** — 異体字セレクタ（U+FE00–FE0F）、ZWJ（U+200D）、ZWSP（U+200B）は
   描かず、エラーにもしない。
5. **行の高さ** — その行で使った書体の最大 ascent ＋ 最大 descent。ヒラギノの行送り（1.5em）は使わない。
6. **読めない書体はエラー** — エラーはファイルではなく書体の単位で返す（.ttc は書体ごとに読めたり
   読めなかったりする）。理由（フォントのどの部分が読めないか）を付ける。

フォントを読むのは起動時で、読むのはランタイムの cmd 層。描画の層（view 層）はファイルを開かない
（gem-agent ADR-0089 §5 / ADR-0090 §5）。

### Input / Output

- 入力: mermaid のソース文字列（コードブロックの囲みは含まない）。
- 出力: `*image.RGBA`。白地のカードに描く。端末の背景色は問い合わせない。
- エラーは次の 3 種類で、どれも行番号を持つ。呼び出し側はいずれの場合もソースを表示する。
  種類を分けるのは、既存の表示が扱いを分けているため（gem-agent ADR-0063 §4: 対応していない種類の図は
  黙ってソースのまま、描こうとして失敗した図はソースに注記を 1 行）。
  - **図の種類が未対応** — state、class、gantt など。
  - **構文が未対応** — 対応する種類の図の中の、このエンジンが描かない構文。
  - **構文の誤り** — mermaid として正しくない。
- 資源の上限: ノード数と画像のピクセル数に上限を置き、超えたら「構文が未対応」と同じ扱いにする。
  上限は、エンコード後の PNG が `termimg.MaxBytes`（2MiB）を超えないように決める。今の
  `drawImage` は上限を超えた画像を黙って描かないので、図がソースごと画面から消えないようにするのは
  組み込み側の要件（§4 第 3 段階）。
- 同じ入力と同じフォントからは、常に同じ画像ができる。map の反復順に依存しないことをテストで固定する。

### 第 1 段階で対応する構文

**基準は mermaid 公式ドキュメント**（mermaid.js.org の Flowchart / Sequence diagram /
Entity Relationship Diagram の各ページ）。**参照した版は mermaid 12.0.0（2026-09-10 公開）**。ドキュメントに書かれていない字句の細部（ノード ID に使える文字、線の記号の読み方、subgraph の所属）は、同じ版の `flow.jison` と `flowDb.ts` で確かめ、その旨をテストに書く。
以下は、その仕様の中から、実データ（Discussion Log）と仕様上の基本構文を合わせて選んだもの。
【実】は実データに現れたもの。

**共通**

- front-matter（`---` で囲む）: `title` はカードの見出しとして描く。`config` は無視。
- ラベル内の `<br>` / `<br/>` は改行。`#quot;` などの文字参照と `#35;` のような数値参照は文字に戻す。
- `%%` コメントは無視。

**flowchart / graph**

- 向き: TD / TB / BT / LR / RL
- ノードの形: 旧来の書き方の 14 種すべて（四角、角丸、スタジアム【実】、サブルーチン、円柱【実】、
  円、非対称、ひし形【実】、六角形、平行四辺形【実】、平行四辺形 alt、台形、台形 alt、二重円）
- 引用符付きのラベル `A["…"]`【実】
- ノード ID: 日本語を含む ID、`End` のような大文字の語【実】（予約語は小文字の `end` だけ）
- 線: 実線・点線・太線、矢印なし、長さ違い（`--->` など）、`o` 端・`x` 端、両端（`<-->` `o--o` `x--x`）
- 線のラベル: `-->|文字|`、`-- 文字 -->`【実】、`-. 文字 .->`、`== 文字 ==>`、`-- 文字 ---`
- 連結 `A --> B --> C`、`&` による一括指定【実】
- 閉路【実】
- subgraph（1 段）【実】。`subgraph id [タイトル]`、`subgraph id["タイトル"]`、
  `subgraph タイトル`、日本語の ID【実】。subgraph を端点とする線【実】
- **subgraph の所属規則** — ノードは、それに**最初に言及した subgraph** に属する。トップレベルで
  宣言しただけでは所属は決まらない。mermaid.js（flowDb の `makeUniq`）と同じ規則。実データの応答で
  subgraph を使う 11 個中 6 個で結果が変わり、規則を誤るとノードが別の箱に入った誤った図になる。

**sequenceDiagram**

- participant / actor、`as` による別名【実】
- メッセージ: `->` `-->` `->>` `-->>` `-x` `--x` `-)` `--)` と双方向の `<<->>` `<<-->>`
- 自分自身へのメッセージ【実】
- autonumber【実】（開始値・増分つきも）
- activate / deactivate、`+` / `-` の書き方【実】
- note（left of / right of / over）【実】
- alt / else / loop / opt / par / and / critical / option / break の枠
- box（参加者のまとまり）
- `rect` は色の指定なので枠だけ無視し、中身は描く

**erDiagram**

- 実体、別名、ハイフンを含む名前・引用符付きの名前
- 属性ブロックの無い実体【実】
- 属性（型・名前・PK / FK / UK とその組み合わせ・コメント）【実】、省略可能な型 `string?`、
  `~` による総称型（`List~int~` は `List<int>` と表示）
- 多重度の全記号と、語による書き方（`one or more` など）。記号はどちら側にも書ける（`o{--||`）
- 識別関係（`--`）と非識別関係（`..`）、関係のラベル（引用符付きを含む）【実】
- `direction`（flowchart と同じ配置を使うので対応する）

**無視するもの（見た目だけの指定）**: classDef、style、class、`:::`、linkStyle、`%%{init}%%`、
click、subgraph の中の `direction`、`~~~`（見えない線。配置のためだけのもの）、accTitle / accDescr。

**未対応とするもの（構文が未対応のエラー）**: 入れ子の subgraph（第 2 段階）、`A@{ shape: … }` の
拡張形状、edge ID（`e1@-->`）、Markdown 文字列（`` "`…`" ``）、sequence の create / destroy と
半矢印・中央接続、ER の subgraph、上に挙げたもの以外の読めない行すべて。

### 配置の仕様

- **flowchart と ER**: ノードを段に分けて並べる方式（Sugiyama 法）を自前で書く。
  1. 閉路の除去: 深さ優先探索で見つかった後ろ向きの線を反転して扱い、描くときに向きを戻す。
  2. 段の割り当て: 最長経路法。
  3. 2 段以上をまたぐ線には、各段に中継点を置く。線のラベルも中継点として 1 段を占める。
  4. 交差を減らす並べ替え: 重心法を上下に繰り返す。同じ順位はソースに現れた順で決め、結果を
     決定的にする。
  5. 座標: 段の中で左から詰め、中継点の列はまっすぐにする。1 本の線から枝分かれするノード
     （合流するノード）は、その 1 本の列に揃える。ある面に線が 1 本だけのノードは、その線の列の
     中央に置く（ひし形なら頂点で線を受ける）。1 対 1 の線でつながる並び（段ごとに 1 つずつ）は、
     全員が届く 1 本の列にまとめて揃える。subgraph を端とする線は枠の中央を狙い、枠どうしを
     結ぶ線でつながる subgraph は中央で揃う。
  6. 線は段の中をまっすぐ縦に通り、段と段の間では「縦・横・縦」の直角の折れ線で列を移る。
     横の部分には隙間の中で線ごとの高さ（トラック）を割り当てるので、線どうしは直角にしか
     交わらない。トラックどうしは 0.8em 離す。2 本の線が互いに相手の列へ移る場合は、片方が空いた
     列を経由する回り道をする。横の部分が別の線の出ていく列を越えるならその線より下で、入ってくる
     列を越えるなら上で曲がる（1 つのノードから扇状に出る線どうしが交わらない）。矢印の手前には
     矢印より長いまっすぐな部分を残す（段の順に逆らう線でも）。列を移る線は、できるだけノードの
     すぐ脇で移る。扇状に出る線を 1 本だけ受けるノードには、その中央で入る（すでにまっすぐな線は
     そのまま）。
     端点はできるだけ、線が向かう列の真上（真下）に置く。
  7. 同じ組の間の複数の線は、面ごとに 0.8em 以上離れた別の端点を持つ。面が足りなければノードや
     枠を大きくする（自分自身への線の端も含め、実際の外形の上で距離を測って確かめる）。自分自身
     への線はノードの脇にループを描き、外側のループは内側のラベルより外から出る。
  8. subgraph: 所属するノードを段の中で隣り合わせに保ち、囲む枠と見出しを描く。subgraph を端点と
     する線は枠の縁で止める。
  9. 向き: TD で配置し、LR / RL / BT は座標を変換して得る。
- **sequence**: 参加者を横に並べ、メッセージを縦に積む。自分自身へのメッセージは右に折り返す。

### Configuration

ライブラリは設定ファイルも環境変数も持たない。フォントなどの設定は gem-agent と lagent の設定に
置き、`FontSpec` にして渡す。キー名と、設定が誤っているときに起動を止めるか既定のフォントで
続けるかは、各ランタイムへ組み込むときの ADR で決める。

### External Dependencies

- `golang.org/x/image`（フォントの読み込み・文字の描画・図形の塗り）。go.mod には
  `golang.org/x/text` と `golang.org/x/sys` も入るが、リンクされるのは `x/text/encoding/charmap` だけ
  （検証パスの実測、バイナリの増分は約 0.4MB）。いずれも Go チームが保守するもの。x/image v0.46.0 は
  go 1.26 以上を要求する。
- この依存は lib-series の「標準ライブラリだけ」という原則の例外なので、RFP だけでなく、ライブラリの
  README / README.ja / AGENTS.md と lib-series のカタログの行にも明記する。更新と脆弱性の確認は
  リリースの前に govulncheck で行う。
- 実行時に使う外部のものは macOS のシステムフォント（`/System/Library/Fonts`）だけ。
  同梱もダウンロードもしない。

## 3. Design Decisions

- **Go で自前実装する。** 使う側の gem-agent と lagent がどちらも Go であることと、組織の外で書かれた
  コードを出荷しない組織の方針（ADR-024）のため。よく使われる作り方（mermaid.js をヘッドレスの Chrome
  で動かす mermaid-cli）は、組織の外のコードをそのまま出荷することになり、Chrome も必要で、起動も
  遅いので採らない。
- **`golang.org/x/image` への依存を認める**（運用者判断、2026-09-28）。フォントの読み込みと描画を
  自前で書くのは割に合わない。Go チームのものなので、一次提供物として扱う（gem-agent も既に
  `x/oauth2` と `x/sys` を直接使っている）。
- **ランタイムの描画機能として作り、モデルのツールにはしない**（運用者判断、2026-09-28）。図を描く
  ツールはモデルがほとんど使わず、使われない機能になる（gem-agent の `render_diagram` は 76 セッションで
  1 回しか呼ばれず、ADR-0063 で撤去した）。
- **gem-agent ADR-0089 の A3（mermaid を PNG にする案の却下）を改める。** A3 の理由は「ADR-0042 の
  忠実性の検査（ラベルが全部あるか・線の数が矢尻の数と合うか）は罫線レンダラのためにあり、PNG に
  すると検査も一緒に消える」だった。あの検査が必要だったのは、中身を見られない他人のレンダラの出力を
  文字列から逆算していたからである。自前のエンジンでは配置の結果を直接調べられるので、検査は
  エンジンの内側に移す。
  - 配置の検査: すべてのノード・線・ラベルが置かれている。ラベルどうし、ラベルとノード、ラベルと
    subgraph の見出しが重ならない。線が端点以外のノードの枠を通らない。多重の線が重ならない。
  - 読み違いは描く段階の検査では捕まらない（過去の失敗は、`-- 文字 -->` を別のノードと誤読した例の
    ように、ラベルは全部あるのにグラフが違うものだった）。これは公式仕様から起こした構文の表の
    テストと、実データの出力を人が 1 枚ずつ見る確認で守る（§4）。「間違いは仕組み上起きない」とは
    言わない。
  - 正式な改訂は、gem-agent への組み込み時の ADR で行う（ADR-0089 に Amended 注記を付ける）。
- **構文の読み取りは描き方と切り離す。** 第 2 段階で罫線表示を自前に置き換えるとき、同じ図の
  データを使うため。
- **白地のカード状の画像にする。** 端末の背景色を問い合わせると、BubbleTea では応答が入力欄に
  漏れた前例がある（gem-agent、2026-08-18）。白地なら明るい端末でも暗い端末でも読める。
- **間違いは防ぎ、見た目の良し悪しは判定しない**（gem-agent ADR-0042 の原則を引き継ぐ）。
  線の交差、図の大きさ、縮めたときの文字の小ささでは表示を拒まない。
- **資源の上限は設ける。** 見た目の判定ではなく、描画が止まらなかったりメモリを使い切ったりするのを
  防ぐため。値は実装時に実測して決める。
- **フォントは選べるようにする**（運用者の要望、2026-09-28）。ただし文字の欠けは間違いとして扱う。
- **OS が管理する役割は担わない。**

**補完する既存ツール**: gem-agent と lagent の `internal/termimg`（画像の表示）、gem-agent の
`internal/diagram`（mermaid フェンスの検出と罫線表示）。

**対象外**:

- flowchart・sequence・ER 以外の図（state は第 2 段階。class、gantt、pie、mindmap、journey、
  gitGraph などは予定しない）。
- テーマ、色の指定、style の反映。
- SVG の出力。
- sixel、および画像を出せない端末への画像表示。これらはいまの表示のまま。
- mermaid の書き方の誤りを直すこと（誤りはエラーにしてソースを表示する）。
- モデル向けのツール、およびシステムプロンプトでの図の指示。

## 7. External Platform Constraints

- 画像を出せる端末は iTerm2 と kitty の方式に限られる。表示できるかの判定と、占める行数・桁数の
  宣言は既存の termimg が担う（gem-agent ADR-0089）。sixel は占める行数を宣言できないので対象外。
- 画像 1 枚あたりの上限は `termimg.MaxBytes`（2MiB）。
- 画像 1 枚を送ってから端末が次の問い合わせに応答するまでは、iTerm2 で 17〜105ms、kitty で 15〜106ms
  （PNG 59〜267KB、段 0 の実測）。端末が受け取りを終えるまでの上限であって、描き終えるまでの時間ではない。
- セルの縦横比は端末と設定で変わる（段 0: iTerm2 は 2.25、kitty は 1.86）。kitty は宣言した行数・桁数
  いっぱいに画像を置くので、比を誤ると図が歪む可能性がある。比は `TIOCGWINSZ` から得る（§2）。
- フォントは macOS のシステムフォントに依存する。対象は macOS だけ（gem-agent と lagent も
  darwin/arm64 専用）。
